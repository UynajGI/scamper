## 1. Independent references and randomized parity (claim 1, 2)

References, all written from scratch for this review (sharing nothing with
production or the committed tests beyond the public `cmc-rs` API):

- **my-Dijkstra-LIFO**: binary-heap Dijkstra whose tie policy is
  insertion-counter LIFO — the *latest-pushed* entry settles first among
  equal distances — deliberately opposite to production's lowest-vertex-id.
  It iterates my own adjacency (raw edge list in insertion order), not the CSR.
- **my-SPFA**: queue-based Bellman-Ford over its own adjacency (a different
  algorithm family; relaxation order entirely different).
- **my-rotBF**: round-based Bellman-Ford with the edge scan rotated per round
  (third reference, n ≤ 64 subset).

Graph generators are my own (xoshiro256++ via splitmix64, seeds
`0xA11CE…/0xB0B…/0xC1A…/0xD1AD…/0x5EED…/0xF…`; disjoint from every committed
seed family). Families: ER multigraphs n ∈ {7,13,25,40,64}, m ≈ 2.8n–3.1n,
self-loop fraction 0.12, forced parallel copies, weight modes
U[0,1) / 30% exact zeros / 60% exact zeros / dyadic {0,0.5,1} / ±3-ulp
jitter around {0.25,0.5,0.75,1,2}; deliberately disconnected graphs
(3–4 components, cross-checked by union-find); grids 6x6–10x10 in four
weight modes; 1-ulp dense graphs with every vertex as source.

**Coverage tally (712 sweep cases):** zero-weight cases 390, parallel-edge
cases 652, self-loop cases 645, disconnected cases 55, 1-ulp cases 192;
18,949 vertex-distance comparisons. **All 712 cases agree BITWISE with
my-Dijkstra-LIFO, all 712 with my-SPFA, and 692/692 (n ≤ 64 subset) with
my-rotBF** — no tolerance needed anywhere. Scale spot-checks: 100,000-vertex
ER (V=1e5, E=3e5) and 40,000-vertex weighted grid, each 0 bitwise mismatches
vs SPFA over every vertex.

This bitwise result is stronger than the committed gate's own policy (1e-12
relative on U[0,1) fields) and is not luck: with non-negative finite weights
the relaxation fixpoint is unique — final dist[v] = min over paths of the
left-to-right f64 sum — and both Dijkstra (final parent distances at settle
time, addition monotone under round-to-nearest) and Bellman-Ford (fixpoint)
compute exactly that set-minimum. Equal-cost ties that round differently
resolve to the smaller representable sum in *both* algorithms. The committed
1e-12 tolerance is therefore conservative, not load-bearing (Note M4).

**Predecessor consistency (my checker, every case):** for each reached vertex
the predecessor edge's endpoints connect parent→child; the hop-sum holds
*bitwise* (`dist[v].to_bits() == (dist[p] + w[e]).to_bits()`, exploiting that
production writes dist and predecessor in the same strict-improvement push
with the parent already settled); chains are acyclic (visited-set per walk),
terminate at the source within n hops; the source and all unreachable
vertices carry `NO_PREDECESSOR` sentinels; `reached` equals the count of
finite distances. 767/767 validations pass. The parallel-edge "lighter bond
wins" property is implicitly pinned by the bitwise hop-sum (a heavier
parallel bond cannot satisfy it); the committed hand case pins it explicitly.

**Tie-policy independence is non-vacuous:** across 267 sweep cases plus the
adversarial family, 2,545 predecessor vertices received a *different* (but
equally valid) predecessor under my LIFO policy than under production's
lowest-id policy, at bitwise-identical distances — so the consistency checks
above genuinely exercise the documented tie policy rather than a single
shared path choice.

## 2. Tie-policy adversarial (claim 2)

Unit-weight open grids 6x6, 9x9, 12x12, 14x14 (massive equal-distance
multiplicity); dyadic-weight grids 8x8 and 11x11 (exact ties with weight
diversity); K20 with unit weight (every vertex tied with every other, all 20
sources); an all-zero dense multigraph (n=30, m=90 + forced parallels +
self-loops — zero-weight cycles everywhere); signed-zero weights (−0.0 mixed
with +0.0 and 1.0); subnormal-weight chains (5e-324, 1e-320, 2.5e-323).
55 further cases, all passing the full parity + path-reconstruction battery.

Additional observations: −0.0 weights pass validation (correct: `-0.0 < 0.0`
is false) and every reached zero-distance vertex has *+0.0 bits* (0x0), never
−0.0 — distances can never be −0.0 since the source is +0.0 and `+0.0 + −0.0
= +0.0`; the rustdoc's `total_cmp(−0.0,+0.0)` "distinct keys" note is
defensive, unreachable in practice (confirmed empirically). The all-zero
multigraph terminates with every reached vertex at exactly +0.0 and a valid
acyclic pred tree.

## 3. Settle-once and the E+1 heap budget (claim 3)

**Re-derivation of the stale check** (`entry.distance > dist[v] → skip`):

1. Pushes happen only on strict improvement, so for each vertex the pushed
   distances are strictly decreasing; no two live entries of one vertex share
   a distance, and distinct vertices have distinct ids — heap keys are unique.
2. `dist[v]` is set to the pushed value at push time and only decreases, so at
   pop `entry.distance ≥ dist[v]` always; `>` means superseded (skip), `==`
   means fresh (settle).
3. The pop sequence is nondecreasing in distance: when a settle at distance d
   relaxes, every push has candidate `d + w ≥ d` (non-negative weights), and
   the heap returns the global minimum.
4. After v settles at d, any later relaxation into v has candidate
   `dist[u] + w ≥ dist[u] ≥ d` (later settles have non-smaller distances), so
   no strict improvement is possible: `dist[v]` is final, v is never pushed
   again, and its fresh pop happens exactly once. A stale entry cannot hide a
   fresh one: the fresh entry has strictly smaller distance and any heap pops
   the minimum first; stale pops are skipped without side effects.

Counterexample attempts — all-zero graphs (equality never pushes), parallel
zero edges, self-loops (candidate ≥ dist[v] always), 1-ulp chains, saturating
weights (INF is never `<` anything) — all failed, as the argument predicts; a
violation would require a negative weight, which validation rejects before
the pass.

**E+1 budget.** Each physical edge {u,v} relaxes at most twice (once per
endpoint settle, each vertex settling exactly once). If u settles first
(`dist[u] ≤ dist[v]` by step 3), u→v may push once; v→u at v's settle has
candidate `dist[v] + w ≥ dist[u]` — never strict, never pushes. Self-loops
never push. Hence pushes ≤ 1 + E, and `try_reserve_exact(edges + 1)` is an
exact bound. My mirror (identical push discipline) never exceeded it on any
of the 767 cases, and **chains achieve it exactly** (pushes = E+1 at
n = 2, 3, 10, 100, 1000) — the reserve has zero slack and is exactly
sufficient. Production-side confirmation: `allocation-counter` around 256
alternating tracking on/off passes per topology, **0 allocations / 0 bytes**
on chain-1000 (the tight case), all-zero-dense-300, grid-30x30,
dense-er E=32,771 ≈ 64V, and ulp-64. Through the public API the bound is
only breakable with negative weights (rejected) or a view violating its
trait contract (each physical edge exactly two incidences), which the trait
docs already license to panic.

## 4. Overflow / saturation (claim 4)

- Chain of 1e308 weights: dist[1] = 1e308, dist[2] = dist[3] = INF
  (1e308+1e308 saturates) reading as unreachable, reached = 2, sentinel
  predecessors on saturated vertices, checker clean.
- Mixed graph where a finite alternative beats a saturating path
  (direct 1.5e308 vs 1e308+0.75e308 = 1.75e308, still finite) and a vertex
  reachable only through sums > f64::MAX reads unreachable while a direct
  1.2e308 edge wins over the saturating 1e308+1.2e308 route.
- Single f64::MAX edge: finite, reachable, bitwise hop-sum holds.
- f64::MAX self-loops at source and non-source vertices: no-ops, no panics.
- Saturated candidates never enter the heap (`INF < INF` is false), so no INF
  distances or NaNs can propagate. This is exactly the documented
  saturation-as-unreachable convention; no guard is needed for the F2/F3 use
  case (weights are physical passage times, many orders below f64::MAX).

## 5. Rejection isolation (claim 5)

My own sequences on a reviewer hand graph (6 vertices, parallel pair, zero
edge, self-loops, isolated vertex — different from the committed one):
negative weight (payload names edge 2, value exact), NaN / +INF / −INF
(WeightNotFinite each), wrong length short (6/7) and long (8/7), source domain
(source = 6 = V, and source = usize::MAX), zero-vertex view (EmptyGraph).
After *every* rejection the distance and both predecessor arrays are bitwise
identical to the pre-rejection baseline (compared as bit patterns), and a
valid rerun reproduces the baseline bitwise. A rejection issued after a
tracking-off run also leaves that run's distances intact. Precedence observed
and consistent (not currently documented): EmptyGraph → length → weight scan
→ source domain. `Display` strings name the offending edge and render
without panic for all non-Capacity variants.

## Findings

- **M1 (Minor — rustdoc inaccuracy, empirically confirmed).**
  `GeodesicTracking::Off` docs: "the predecessor arrays are left untouched
  (their contents are stale from the last tracking-on run and must not be
  read)". False: `first_passage_run` calls `workspace.prepare(...)` on every
  run, and `prepare` → `reserve_exact` unconditionally executes
  `clear(); resize(len, default)` on **all four** buffers — so after a
  tracking-off run the predecessor arrays are all `NO_PREDECESSOR`, not stale
  (my E9 probe: all-sentinel after a tracking-on → tracking-off sequence).
  No correctness impact (the contract says do not read them, and sentinel is
  arguably safer than stale), but the documented observable behavior via
  `predecessor_vertices()` is wrong. One-line doc fix, or state the sentinel
  reset explicitly. Also worth noting `prepare`'s double write (defaults in
  `prepare`, then `reset`) is harmless but makes `reset`'s tracking-dependent
  predecessor fill redundant.

- **M2 (Note — Capacity rejection corner).** The rustdoc says rejections are
  raised "before the workspace is touched, so a rejected call leaves the
  previous run's results intact". True for all five validation rejections
  (verified), but the `Capacity` variant is raised *inside* `prepare` after
  the heap was cleared, and in the distance-reserve failure path
  `reserve_exact` has already `clear()`ed the distance vector before the
  failed `try_reserve_exact` — so an allocation failure would destroy prior
  exposed results. Practically indistinguishable from process death by OOM;
  documenting the exception (or reordering the clear after the reserve
  attempt) would close it. No action required for F2.

- **M3 (Note — roadmap wording drift).** Roadmap v2 §3 F1 specifies
  "reusing E1's `ProcessQueue`/counter discipline"; the implementation
  instead uses its own `BinaryHeap<Reverse<PassageEntry>>` keyed
  `(total_cmp distance, vertex id)` — the invasion-frontier tie discipline —
  and documents the rationale (16-byte entry, no counter field) in rustdoc
  and the PERCOLATION.md row. The roadmap text was not updated. Design choice
  is sound and better documented than the spec; only the spec is stale.

- **M4 (Note — conservative tolerance, strengthening available).** The
  committed parity gate allows 1e-12 relative on U[0,1) fields on the theory
  that tie-broken paths may round differently. The relaxation fixpoint is
  bitwise-unique for non-negative weights, and 767 randomized + 140,000
  at-scale comparisons against two independent implementations (deliberately
  different tie policies) show bitwise agreement everywhere. Future stages
  can assert bitwise parity and drop the tolerance.

- **M5 (Note — naming collision).** PERCOLATION.md now contains two distinct
  "F1" stages: the v1 read-only topology capability (§"F1 read-only topology
  capability") and the v2 weighted shortest-path row (labelled "Roadmap v2
  §3 F1"). Inline disambiguation exists; a renamer pass is not worth it, but
  reviewers grepping "F1" should be aware.
