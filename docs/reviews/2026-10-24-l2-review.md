## Overall verdict

**No Blocker. Two Major findings. Do not mark L2 Validated yet.**

The core L2 realization is correct: the occupancy replay is bit-identical to
L1/law on 1,188 independent runs (21,549 checks, 0 failures), profiles and
diameters match an independently written BFS/all-pairs reference bit-for-bit
including INFINITY on `[1]`, `[2]`, `[5]`, `[3,4]`, `[5,5]`, the draw stream is
bit-identical across layers, the estimator arithmetic is correct, all typed
validation rejections and precedence hold, the allocation probe is genuinely
zero-allocation, and the s<=1 / s=2 observables are kept apart as the paper
requires.

Two things do not hold up as stated:

1. **The s = 2.5 linearity gate is statistically underpowered and
   seed-fragile** at its committed `R = 12`: 7/10 fresh seed bases pass; 2/10
   produce a negative `c`, 2/10 violate `high < 1.05`, and the measured ratio
   is not monotone in some seeds. At `R = 24` the same gate passes 6/6, so
   the physics is supported but the committed gate is not a reliable
   statistical bracket.
2. **`ChemicalDistanceWorkspace::occupied_edge_count()` returns `pairs`
   before the first run** (and after any bare `prepare`), because `prepare`
   sizes the neighbor buffer to `2 * pairs`; the documented "last run's
   occupied edge count" is silently wrong and contradicts
   `last_outcome().occupied_edges == 0`. The same reservation makes the
   "empty before the first run" / "untouched pages cost nothing" docs false.

## Findings

### Blocker

None.

### Major

**M1 — the committed s=2.5 gate is not statistically robust (seed-fragile at
R=12).**
`CMC.rs/tests/physics/long_range_distances.rs:612-617` fixes `N=8192`,
`REALIZATIONS=12`, grid `256..2048`; the assertions are
`:671-708` (`low>0.8`, `high<1.05`, `deficit>0` at `:681-684`, ratio
non-increase at `:690-704`, strict decrease at `:705-708`). At the committed
seed it prints `c=12.8134±12.1035`, i.e. the 95% interval barely excludes
zero, and the doc reports `c = 12.8 > 0` without uncertainty
(`CMC.rs/PERCOLATION.md`, L2 row; PERCOLATION L2 section "s=2.5 linear
regime"). With 10 fresh seed bases at exactly the committed settings, my
independent run gives **7/10 full-gate pass**: two bases have `c < 0`
(-2.57, -1.06), two have slope-CI upper bounds above 1.05 (1.066, 1.071; one
of those is the same negative-c base), and the ratio sequence in one base
rises 0.3869 -> 0.3900 -> 0.4042 -> 0.3893 (strict decrease fails). At R=24
the gate passes 6/6 (A = 0.352-0.370, c point-positive 7.8-13.8), so the
linearity conclusion is supported; the committed gate is simply
underpowered. Repro: `/tmp/l2rev/target/release/l2rev s25seeds` and
`s25seeds24` (source `/tmp/l2rev/src/main.rs`), and the committed command
below. Fix: raise `REALIZATIONS` to at least 24 (48 preferable), report
`c ± t*se` and assert a CI (or at least require the point estimate to be
stable across a second seed), and replace "decreases monotonically" with the
actual non-increase-within-noise claim.

**M2 — `occupied_edge_count()` returns `pairs` before the first run; pre-run
adjacency docs are false.**
`prepare` calls `reserve_exact(&mut self.neighbors, 2*pairs, 0, "neighbors")`
(`CMC.rs/src/percolation/long_range_distances.rs:166-172`), and
`reserve_exact` always `clear()`s then `resize(size, fill)` (`:243-250`), so
after `prepare` the neighbor Vec has length `2*pairs`. The accessor is
`neighbors.len()/2` (`:224-227`). Therefore
`ChemicalDistanceWorkspace::new().prepare(5,10,4)` — and, more importantly,
`ChemicalDistanceSampler::new(box_[5], 1.0, 1.5, &[0])`, which prepares in
`new` — reports `occupied_edge_count() == 10`, while
`last_outcome().occupied_edges == 0`; the sampler has never run. My repro:

```
pre-run sampler state: workspace.occupied_edge_count=10 offsets_len=6
neighbors_len=20 profile_len=5 all_inf=true
```

The docs say "Occupied edge count of the last run" (`:224`) and "empty before
the first run" for the profile and adjacency accessors (`:204`, `:208-220`),
and "resetting all state" for `prepare` (`:156-159`); all are false after a
bare prepare (the profile is `vertices` copies of INFINITY, the offsets are
`vertices+1` zeros, the neighbors are `2*pairs` zeros). It also makes
"untouched pages cost nothing" (`:128`) and "a same-size re-prepare touches
nothing" (`:231-233`) false: the full `2*pairs` neighbor buffer is written on
every prepare. Fix: reserve neighbor capacity without
resizing (e.g. `try_reserve_exact` then `clear()`), let the run resize to
`2*occupied_edges` as it already does, and add a pre-run accessor test.
This does not affect any committed gate (they all query after a run), but it
is a silent public-API wrong answer.

### Minor

**m1 — estimator NaN documentation contradicts the code.**
`estimate`'s doc says never-reached entries have "NaN mean and error"
(`CMC.rs/src/percolation/long_range_distances.rs:695-697`), but the code
returns `0.0` SE for every `count < 2` (`:720-729`), and the field doc says
"0.0 below two reachable samples" (`:773-774`). Repro: beta=0 sampler,
source 0, three profiles -> entry 1 has NaN mean and SE exactly 0.0. The
committed estimator test (`tests/physics/long_range_distances.rs:311-325`)
only checks SE inside `finite.len() >= 2`, so it never exercises count 0 and
cannot catch this; its stated "minimum reachable fraction 0.40" also means
the "NaN conventions are exercised" claim in `PERCOLATION.md` is untrue for
the never-reached case. Align the doc/code and add the beta=0 case.

**m2 — public overflow panics / silently wrong diameter arithmetic.**
`ChemicalDistanceWorkspace::prepare(usize::MAX, 0, 0)` panics in debug at
`:166` (`vertices + 1`); `prepare(1, 0, usize::MAX)` panics at `:176`
(`distance_range + 1`); in release the first wraps and later fails Capacity
at cursors. `ChemicalDistanceEstimator::add_diameter(usize::MAX)` panics in
debug at `:692` (`diameter * diameter`) and in release silently reports
`mean = 9.223372036854776e18`, `SE = 0` (square wrapped). None is reachable
from a valid box/outcome (diameter is capped at 4095), but these are public
methods. Use checked/saturating arithmetic and/or validate `diameter <
vertices`, and compute the square in f64 (`(d as f64) * (d as f64)`).

**m3 — a capacity failure in `prepare` clobbers the previous adjacency,
contrary to the run doc.**
`chemical_distance_run` says "rejections leave it untouched"
(`:276-278`). Validation rejections do; a `try_reserve` failure does not.
Repro: run a valid `[6]` realization (profile len 6, offsets len 7, 8
edges), then `workspace.prepare(4, usize::MAX/2 + 1, 0)` -> `Err(Capacity {
buffer: "neighbors" })`; afterwards offsets len is 5 (clobbered), edges is 0,
profile is unchanged — an inconsistent workspace. Either make prepare
transactional (reserve into temporaries, commit on success) or document that
only validation rejections preserve state.

**m4 — the s=0.5 gate is numerically degenerate (though its wording is
careful).**
`tests/physics/long_range_distances.rs:737-771` explicitly says finite boxes
may sit above the a.s. sup and quotes Biskup's `D_N` statement qualitatively,
so it does not claim convergence. The numerical gate is still degenerate:
`REALIZATIONS=2`, committed output mean 3.000 at every n with
`slope=0.0000±0.0000 CI=(0,0) R2=NaN`; my 130 fresh realizations all give
diameter exactly 3. It establishes boundedness (`mean <= 4`, no positive
growth), not the value 2; the interval's lower edge 2 is nearly automatic (a
non-complete connected box has diameter >= 2). This is acceptable as a
*boundedness* envelope, but the zero-width "CI" and NaN R2 should be handled
or explicitly described as a constant-sequence artifact, and the report
should not imply the constant 2 is measured.

**m5 — "slower than any power" and "approaches 1 from below" overclaim the
assertions.**
`tests/physics/long_range_distances.rs:20-21` says "strictly slower than any
power"; the assertion is `power_slope + t*se < 0.5` (`:529-534`), which a
power `r^0.4` would pass. Similarly the s=2.5 doc/comment says the effective
slope approaches 1 from below and the O(1/r) deficit keeps it below 1
(`:627-632`), but the assertion only requires `high < 1.05`; fresh seeds
produced point slopes 1.003 and 1.008 that would pass that condition. Reword
as an empirical exponent bound / CI in the window, not a proof of
sub-polynomial behavior or of monotone approach from below.

**m6 — diameter-mode allocation probe omits the bytes assertion.**
`CMC.rs/benches/percolation_allocations.rs:1761-1765` asserts only
`info.count_total == 0` for the diameter path; the three profile probes assert
both count and bytes. Measured bytes are 0 here, so nothing failed, but add
the bytes assertion for symmetry and future safety.

**m7 — s>2 literature citation is about `D_N`, not the typical distance.**
Biskup archive lines 269-273: "we expect that `D_N` scales linearly with
`N`. The latter seems to have been proved only in `d = 1` [6]". The module
(`long_range_distances.rs:62-66`) says "linear chemical distance with a
positive time constant (proved in d=1, Benjamini-Berger)". The tested
typical-distance linearity is true for this law, but the anchor quote is a
diameter statement; cite `D_N` or add a sentence distinguishing the two.

### Notes

- The committed n=8192 sampler reserves `2*pairs` usize + `pairs` f64
  (~805 MB) and the test suite needs >1 GB for the s=2.5 gate; acceptable on
  this host but worth stating for CI. The module says "no cap beyond memory".
- `DIAMETER_VERTEX_CAP = 4096` is a hard cap, not a feasibility guarantee: at
  the complete-graph worst case the all-vertex pass is `O(V^3)` ~ 6.9e10 edge
  traversals, not "feasible to `2^12`" as the cost-model doc suggests. The
  tested beta=1 sparse case is fine.
- The rich regime/cost rustdoc lives on a private module (`mod
  long_range_distances;`), so it is not visible in generated public docs;
  public items say "see the module documentation". Same pattern as L1.
- `add_profile` validates length only; NaN/negative entries are silently
  treated as unreachable or accumulated. `add_diameter` does not validate
  `diameter < vertices`. Public-API hardening, not a stage-gate issue.
- `ChemicalDistanceEstimate` derives `PartialEq` while fields may be NaN, so
  two identical estimates with an unreached entry compare unequal; harmless
  here, surprising as a public equality.
- L1 follow-ups from the previous review are verified fixed: the
  `coordinates()` round-trip is correct on `[3,4]` and `[5,5]` for every
  vertex, and the `PairUniverse` comment now says O(log V). L1's 9 tests
  still pass.

## Follow-ups (priority order)

1. Fix M2: reserve the neighbor capacity without resizing (leave length 0),
   add a pre-run `occupied_edge_count == 0` / empty-adjacency test, and
   correct the "untouched pages"/"empty before first run" wording.
2. Fix M1: raise the s=2.5 realization count to at least 24 (48 preferred),
   print `c` with its CI, assert the intended uncertainty (or a second
   independent seed), and replace the monotone wording with the actual
   non-increase-within-noise assertion. Re-check the PERCOLATION numbers at
   the new R.
3. Align the estimator NaN docs with the code (or return NaN SE for count 0),
   and add a beta=0 never-reached test.
4. Harden the public overflow paths (`prepare` checked `vertices+1`,
   `distance_range+1`; `add_diameter` checked/f64 square) and make or document
   the capacity-failure state.
5. Decide what the s=0.5 gate is allowed to claim: keep it as a boundedness
   envelope and report "diameter 3, not converged to 2", or extend N until
   the approach to 2 is visible. Guard the constant-fit R2 NaN.
6. Reword "slower than any power" / "from below"; fix the `D_N` citation
   nuance; add the diameter-probe bytes assertion.
7. Optional: make the regime module docs public (or link PERCOLATION.md) and
   state the ~805 MB footprint of the n=8192 test.
